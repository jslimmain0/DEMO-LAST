## D-01. 상세 왕복 후 목록의 검색 맥락이 사라진다

**사용자 목적:** 여러 비슷한 워크플로를 검색 결과에서 연속 확인하거나 수정한다.

**재현:** 개인 워크플로 목록에서 `failure-notification` 검색 → 2개 결과 중 `lab-1790961173894 failure-notification` 열기 → 아무것도 수정하지 않고 편집기 왼쪽 `워크플로 목록` 클릭. 같은 동선을 2회 수행했다.

**실제 결과:** 검색어가 빈칸으로 바뀌며 `홈`, 전체 32개 목록으로 돌아온다. 마지막 하나는 최근 작업으로 다시 열 수 있지만 두 번째 검색 결과를 확인하려면 검색을 다시 입력해야 한다. Mock에서도 `/notify` 검색 → Mock 열기 → `목록으로` 복귀 시 검색어가 사라져 6개 전체 목록으로 돌아오는 것을 확인했다.

**기대 근거:** 목록 UI가 검색 결과라는 명시적 작업 집합을 만들고 상세의 버튼이 `목록으로` 돌아가는 행동을 제공한다. 결과 여러 개를 비교하는 작업에서는 출발한 집합을 이어 볼 수 있어야 한다. 단, 현재 `목록`을 소속 폴더의 홈으로 정의한 의도와 충돌하는지는 토론이 필요하다.

**증거:** `docs/images/discovery-2026-10-03/01-flow-search-before.png`, `02-flow-search-return.png`, `08-mock-search-return.png`.

**코드 근거:** `frontend/src/routes/Dashboard.tsx:63`의 검색, 정렬 및 페이지 상태가 컴포넌트 로컬 상태다. `frontend/src/routes/Editor.tsx:516`은 출발 목록이 아니라 흐름의 소속 폴더 주소로 복귀한다. `frontend/src/routes/MockServers.tsx:54` 역시 검색을 로컬 상태로 시작한다. 프론트 담당자가 독립적으로 같은 원인을 확인했다.

**기존 목록과 차이:** 대량 검색 추가의 중복 제안이 아니라 상세 왕복에서 이미 입력한 검색이 사라지는 문제다. 새로운 전역 검색이나 자원 도메인이 필요하다고 전제하지 않는다.

**영향도:** 중간. 데이터 손실은 없으나 여러 항목 확인 시 반복 탐색이 누적된다. 워크플로 32개에서 실제 재현했으며 수천 개의 작업 시간을 측정한 것은 아니다.

**반증·대안:** 최근 작업은 마지막 한 흐름의 재진입을 돕지만 검색군을 보존하지 않는다. 의도적으로 폴더 홈으로 이동하는 버튼이라면 별도 출발 결과 복귀와 구분할 수 있다. URL 또는 공간별 세션 상태 중 어느 방식을 쓸지는 구현 결정 전 합의해야 한다. 다른 공간의 검색을 무조건 재사용해서는 안 된다.

**상태:** 재현 → 토론 → 조건부 채택. 탐색에서 개발 목록에 추가, 수정 미착수. 아래 교차 검토 결정 참조.

## D-02. 실행 이력의 검색 결과와 요약·빈 상태가 서로 다른 사실을 말한다

**사용자 목적:** 특정 흐름의 실패 횟수와 존재하는 기록을 정확하게 파악한다.

**재현 A:** 실행 이력에서 `failure-notification` 검색. 결과 2행이 모두 실패인 상태를 확인한다.

**실제 결과 A:** 머리에는 `2건 ✓ 34 ✕ 7`이 한 줄에 표시된다. 2건은 검색 결과이고 성공 34·실패 7은 검색 전 원본 44건의 집계지만 범위 구분이 없다.

**재현 B:** 같은 화면에서 `discovery-no-such-flow` 검색.

**실제 결과 B:** 큰 빈 상태에 `아직 실행 이력이 없습니다` / `워크플로를 열어 ▶ 실행하면 여기에 기록됩니다.`가 뜨고, 그 아래에 `이 조건에 해당하는 실행이 없습니다.`도 함께 표시된다. 기존 44건은 여전히 존재하므로 최초 실행을 안내하는 문장은 이 상황을 잘못 설명한다.

**기대 근거:** 결과가 0인 검색과 저장된 기록 자체가 없는 상태는 다르다. 한 줄의 건수·성공·실패 집계는 같은 범위이거나 각각의 범위를 명시해야 한다. 필터를 바꿔 찾을 수 있는 기록을 새 실행으로 만들도록 유도할 이유가 없다.

**증거:** `docs/images/discovery-2026-10-03/04-history-filter-counters.png`, `05-history-empty-filter.png`.

**코드 근거:** `frontend/src/routes/Executions.tsx:64` 및 65의 성공·실패 집계는 `all`, 82의 건수는 `rows`를 사용한다. 130의 `rows.length === 0`과 137의 `all.length > 0 && rows.length === 0`가 함께 참이 된다. 프론트 담당자가 관찰 전에 빈 상태 후보를 제안했고 브라우저에서 독립적으로 재현했다.

**기존 목록과 차이:** 저장·실행 성공 및 환경 경계 검증과 별개로, 이미 존재하는 이력을 검색하는 화면의 정보 정확성 문제다.

**영향도:** 중간. 결과를 오독하거나 없다고 생각할 수 있다. 실행 데이터 자체의 손실·누락은 관찰하지 않았다.

**반증·대안:** 전체 성공·실패를 계속 제공하려는 의도라면 검색 건수와 분리해 전체 범위를 표시할 수 있다. 가장 작은 대안은 요약을 `rows`에 맞추고 최초 빈 상태와 필터 빈 상태를 구분하는 것이다. 프론트 담당은 `all`도 상태·기간 서버 필터 뒤의 자료라는 반례를 제시했다. 따라서 `all=0`만으로 최초 빈 상태를 판단하면 안 되고 기본 전체 상태·전체 기간·빈 검색일 때만 사용한다. 최근 200건 밖 검색 한계는 소스에서 확인한 별도 후보이며, 이 회차의 44개 자료로는 실증하지 않았다.

**상태:** 재현 → 토론 → 채택. 탐색에서 개발 목록에 추가, 수정 미착수. 아래 교차 검토 결정 참조.

## D-03. 키보드로는 실행 결과를 읽는 상세 진입을 할 수 없다

**사용자 목적:** 키보드로 검색한 실행의 요청·응답과 실패 원인을 확인한다.

**재현:** `failure-notification` 검색 → `30일` 필터에 포커스 → Tab. 포커스는 첫 행의 `재실행`으로 이동한다. 다시 Tab 하면 `편집`으로 이동한다. 행 제목에 별도 상세 열기 제어는 없다. 재실행 버튼은 누르지 않았다.

**실제 결과:** 마우스로 행 이름을 누르면 정상 상세 모달이 열리지만, 결과 읽기 행 자체는 Tab 순서에 없다. 키보드에 제공되는 행 작업은 재실행 및 편집이다. DOM은 상세 행을 `DIV`, `role=null`, `tabIndex=-1`로 확인했다.

**기대 근거:** 실행 결과 읽기는 이 화면의 핵심 행동이며 마우스 클릭에는 제공된다. 키보드 사용자도 같은 읽기 행동을 수행할 수 있어야 한다. 일반적인 스타일 선호가 아니라 실제 제공된 주요 행동의 입력 방식 차이다.

**증거:** `docs/images/discovery-2026-10-03/06-history-keyboard.png`; 실제 Tab 두 단계와 DOM 관찰. 이미지의 포커스만으로 동작 전체를 입증했다고 주장하지 않는다.

**코드 근거:** `frontend/src/routes/Executions.tsx:144`의 상세 행은 `onClick`만 있는 div이고, 155·156의 버튼과 링크만 기본 키보드 제어를 제공한다.

**기존 목록과 차이:** 대량 이력 출력이나 에이전트 배지의 개선이 아니라 기존 이력을 읽는 작업 접근성이다.

**영향도:** 키보드 사용자에게 높음. 마우스 사용자는 정상 접근 가능하다.

**반증·대안:** 키보드로 편집기에 진입할 수는 있지만 해당 과거 실행 결과를 여는 동일 행동은 아니다. 명시적 `상세 보기` 버튼 또는 제목 버튼이면 기존 행 전체 클릭도 유지할 수 있다. 자식 재실행·편집을 포함한 전체 행을 중첩 button으로 바꾸는 것은 피해야 한다.

**상태:** 재현 → 토론 → 채택. 탐색에서 개발 목록에 추가, 수정 미착수. 아래 교차 검토 결정 참조.

## 정상 확인과 이번 회차의 한계

- 이름 검색은 32개 중 일치하는 두 흐름을 실제로 찾았다. 목록 자체의 검색 실패로 보고하지 않는다.
- 실패 상세는 실패한 `assert`와 조건 `false`, 요청 `assert ( false )`, 실패 응답을 보여주었다. 이전 실행이 없는 경우 그 사실도 표시했다. 근거: `03-history-failure-detail.png`.
- Mock 검색은 `/notify`가 들어간 항목을 찾았고, 편집기에서 `POST /notify`를 선택하면 메서드·경로·응답 `OK`를 확인할 수 있었다. 경로 검색 직후 첫 라우트가 열려 한 번 더 선택해야 하지만 이 자료의 4개 라우트에서는 작업을 막지 않아 별도 결함으로 채택하지 않는다. 근거: `07-mock-route-edit.png`.
- 저장·불러오기·권한 변경을 수행하지 않았으므로 해당 동작의 통과를 주장하지 않는다. 새 Mock 요청이나 기존 워크플로 재실행도 하지 않았다.
- 200건 밖 이력 검색, TCP 미리보기 응답 경쟁, 다른 공간으로의 import 의미, 대량 라우트 탐색은 다음 탐색 후보다. 아직 실증하지 않은 소스 후보를 확정 결함으로 올리지 않는다.
- 제품·프론트 담당자에게 반론을 요청해 아래 범위로 채택했다. 구현은 시작하지 않았다.

| D-01 | 동일 공간에서 출발한 목록의 검색·정렬·페이지·폴더로 복귀한다 | 모든 이전 상태를 무조건 보존하는 안은 제품 담당이 반대했다. 공간 변경이나 직접 URL 진입에는 다른 작업의 검색을 적용하지 않는다. 출발 맥락 없는 직접 진입은 소속 폴더 fallback을 유지한다. Mock의 같은 현상은 별도 정책 추가 없이 동일 사용자 목적을 적용할지 구현 전 확인한다. | 검색 결과 두 개를 연속 열어 읽고 목록으로 돌아와도 검색 집합이 유지됨. 다른 공간과 직접 진입에는 잘못된 이전 필터가 적용되지 않음. |

구현 전 확인할 기술 반례도 프론트 담당에게 받았다. D-01에 router state만 추가하면 `WorkspaceContext.tsx:92`의 space 보충 `navigate(replace)`에서 그 state가 사라질 수 있다. 카드 진입부터 현재 공간을 URL에 명시하거나 같은 공간 정규화가 state를 보존해야 한다. 복귀 맥락은 공간 및 서버·계정 식별 범위를 확인하고 다른 범위에서는 폐기한다. D-03 버튼은 행 클릭과 이벤트가 겹치지 않도록 하며 기존 재실행·편집 버튼과 별개로 동작해야 한다. 이는 구현 지침이며 아직 수정·검증한 상태는 아니다.

## 다음 탐색 회차를 위한 인수인계

브라우저 슬롯은 첫 회 종료 후 주 담당에게 반납했다. 전용 탭은 18182 개인 Mock 목록이며 미저장 변경·권한 변경·새 실행은 없다. viewport override와 네트워크 차단은 적용하지 않았다. 다음 회차는 새 실행 번들을 확인하고 위 세 항목과 이미 해결된 이전 제품 재검토 항목을 먼저 대조한다.

다음 회차는 아래 중 아직 관찰하지 않은 사용자 여정 1~2개를 선택한다. 발견을 만들기 위해 계속 같은 목록을 재검사하지 않는다.

1. **동료의 정의 재사용:** 현재 가져오기·내보내기·버전 화면에서 대상 공간과 덮어쓰는 범위를 사용자가 이해할 수 있는지 확인. 실제 데이터 변경은 격리 fixture에만 수행한다. 새 매니페스트를 미리 해법으로 정하지 않는다.
2. **처음 받은 복잡한 흐름 이해:** 어떤 노드의 입력이 어디서 오는지 찾고, 작은 수정 후 다시 원본과 비교하는 동선. 새 온보딩 마법사가 필요하다고 전제하지 않는다.
3. **이전 실행 찾기:** 200건 이상 이력이 있는 격리 자료에서 알려진 오래된 실행 검색. 지금은 소스 후보일 뿐이며 사실 확인 전 결함으로 승격하지 않는다. 불필요한 실제 호출로 이력 수를 채우지 않는다.
4. **프로토콜 편집 전후 미리보기:** 지연된 미리보기 A가 노드 B로 전환한 후 잘못 나타나는지 여부. 응답 순서를 제어할 격리 fixture를 먼저 구성하고, 이 탐색을 실제 외부 TCP 요청 테스트와 혼동하지 않는다.

중복 기준: `product-rework-decisions/validation`의 관리·환경 목적지·Mock 주소 진단·긴 사이드바, 이 문서의 D-01~03은 새 발견으로 다시 세지 않는다. 다른 사용자 목적에서 추가 영향이 확인되면 새 티켓 대신 기존 항목의 근거를 보강한다. 재현하지 못한 후보, 정상 동선, 도구의 제약도 함께 기록한다.
