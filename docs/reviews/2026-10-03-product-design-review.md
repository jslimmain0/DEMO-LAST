# FlowLink 제품·디자인 검토 기록

검토일: 2026-10-03. 이 문서는 실제 논의와 반박, 채택한 수정, 확인한 증거를 기록한다. 최종 릴리스 판정과 전체 검증 결과는 root의 별도 요약에서 다룬다.

## 참여 범위

실제 하위 작업자는 네 명이다. 후속 시각 검토를 별도의 신규 인원으로 계산하지 않는다.

| 작업자 | 실제 범위 | 이 기록의 근거 |
|---|---|---|
| workbench | 공간 라이브러리·고정 작업 공간 셸·워크플로 목록 초안 | `.run/ui-review/workbench-notes.md`의 제안과 선택 근거 |
| resource | 환경·시크릿 관리, 저장 실패·권한·초안 처리, 후속 자원 화면 압축 | 담당자와 제품 검토자의 실제 메시지 교차 검토. 테스트 통과 보고는 해당 담당자 보고로 구분 |
| product | 독립 제품·도입 검토. 이후 같은 작업자가 저장된 실제 화면의 시각 검토, 일부 후속 수정, REST 대량 fixture 생성도 수행 | `.run/ui-review/product-adoption-review.md`, 직접 읽은 소스·이미지·명령 결과 |
| oracle | Oracle·Vault와 백엔드 통합·실행 검증 범위 | 이 제품 검토 문서는 그 담당자의 최종 테스트 결과를 직접 재현하지 않았으므로 성공 여부를 대신 판정하지 않음 |

root는 통합, Editor·Mock와 라우팅 등 조정, 실제 브라우저 조작과 캡처, 최종 빌드·릴리스 요약을 맡았다. 추가 독립 작업자 생성은 도구의 thread limit으로 거절됐고, 기존 product 작업자에게 시각 검토가 이어졌다. 별도의 마케팅·QA·시각디자인 인원을 추가했다고 주장하지 않는다.

## 고정한 제품 모델

- 실행 위치는 사용자 PC 하나와 회사 서버 하나다. 여러 에이전트나 서버 군집 선택 화면을 만들지 않는다.
- 개인 작업은 해당 PC에, 공용·팀 작업은 회사 서버에 저장한다. 워크플로의 저장 공간과 각 노드의 실행 위치, 노드가 사용하는 자원 공간은 구분한다.
- 한 워크플로에서 PC·서버 실행을 섞을 수 있다. 환경 변수와 시크릿은 실제 적용되는 공간·환경을 확인할 수 있어야 한다.
- 개발자가 설치 앱·트레이·기본 브라우저 로그인·IDE 연결을 거쳐 첫 호출을 성공시키는 것이 도입 목표다. 데모용 숫자를 많이 보여주는 것은 그 목표의 검증이 아니다.

## 실제 논의와 결정

| 논점 | 제안·반박 근거 | 채택한 최소 수정·상태 |
|---|---|---|
| 수백 개 팀 탐색 | workbench는 별도 `/workspaces` 라이브러리를 제안. 상시 공간 트리는 1280px 에디터의 팔레트·속성·실행 패널에 추가 폭을 요구하므로 제외. product는 초안을 권위로 보지 않고 소스와 기존 화면을 독립 검토 | 별도 검색·분류·즐겨찾기 라이브러리, 현재 공간 전환 메뉴를 유지. 빈 글로벌 사이드바를 장식용 지표로 채우자는 보완은 필요성이 확인되지 않아 채택하지 않음 |
| 저장 공간·실행 위치·자원 소유자 | PC/서버 색상과 이름만으로는 팀 A에 저장한 흐름이 팀 B의 자원을 사용하는 경우를 설명하지 못함. 실행 계획의 자원 공간 누락을 product가 지적 | 라이브러리에 실제 서버 주소·계정, 전환 메뉴에 짧은 ID. root는 실행 계획의 자원 공간 표시를 담당. 전체 캔버스 재작성은 제외 |
| 동명 공간 | 이름만 있는 전환·자원 선택을 문제로 지적. 실제 fixture 작성에서 서버 REST가 동일 팀 이름을 400으로 거부함 | UI에는 ID 구분을 보완. 검증 데이터는 `결제팀`, `결제팀 · 검증 A`, `결제팀 · 검증 B`로 조정. 정확한 동명 팀 세 개를 검증했다고 주장하지 않음 |
| 로그인·승인·참여 구분 | 공간 없음이나 API403을 승인 대기로 추측할 수 없다는 root 반박을 채택. 현재 개인 공간의 API로 회사 가입 상태를 읽는 것도 잘못된 범위 | 서버 API의 실제 `myStatus`로 PENDING/BLOCKED를 표시. 승인된 사용자에게 라이브러리 팀 생성, 참여 팀이 없으면 기존 팀 관리자에게 멤버 추가 요청 안내. 상태 조회 실패는 별도 재시도 |
| 환경 실패 후 실행 | product가 Editor의 `ensureEnvLoaded().catch(() => {})`를 찾아 환경 로드 실패가 빈 환경 실행으로 이어질 수 있음을 P1으로 제기 | root와 resource가 실행 준비·저장 완료 확인 경로를 수정. 최종 정상 실행·노드 단독 실행·재개 경로의 검증 결과는 릴리스 요약에서 별도 확인 |
| 첫 성공 동선 | 빈 워크플로와 자원 메뉴만으로 Mock→HTTP 호출→결과가 연결되지 않음. 모든 사용자를 Mock부터 시작시키는 것은 기존 실제 API 사용자를 방해 | Dashboard의 기본 행동은 새 워크플로. 기존 API는 cURL/OpenAPI 안내, 대상 API가 없는 사용자에게 현재 공간의 Mock 링크. root는 Mock·Editor의 짧은 첫 호출 안내 담당 |

| 편집기 상단 밀도 | root가 저장 문맥·이름·많은 버튼이 한 줄에 섞여 줄바꿈되는 문제를 제시. product는 도구 그룹 분리에는 동의하되 자원 공간과 실제 환경 표시가 우선이라고 반박 | root가 공간·워크플로·저장 상태와 편집·환경·실행·저장 그룹을 최소 변경으로 정리. 명시적인 실행 계획 진입점 제안 |
| 자원 페이지와 다이얼로그 | 독립 페이지 추가만으로 기존 환경·시크릿 다이얼로그의 다른 초안·실패 처리 문제가 사라지지는 않음 | 공통 패널·스토어 재사용, 에디터의 자원 관리 진입 링크. 저장 실패·재시도·미적용 변경·VIEWER 처리는 resource 범위 |
| 페이지 높이 사용 | 실제 환경 캡처에서 공간 표시 세 번, 제목 두 번, 긴 설명 때문에 363개 변수 중 두 줄만 노출. 단순 글자 축소는 읽기와 입력을 해침 | product와 resource가 독립적으로 같은 결론: full-page에서 내부 제목·공간 설명을 생략하고 활성 환경·저장 상태를 한 번 표시. 도움말·비교는 접기. 다이얼로그는 자체 문맥 유지. 최신 캡처에서 변수8줄·환경9줄 확인 |

## 증거 수준

### 소스·정적 검사

product는 Workspaces, WorkspaceSwitcher, AppShell, WorkspaceContext, Dashboard, Editor, SettingsDialog, Resources, EnvSwitcher, 환경·시크릿 패널, ResourceScopeNote, AgentSettings, ExecutionPlanDialog 등을 읽었다. 직접 담당한 수정은 공간 목록·전환·CSS, Dashboard 빈 상태·복구 안내, 후속 remoteLoading 필드이다.

해당 수정 뒤 `npx tsc -b --pretty false`와 변경 파일 oxlint가 통과했다. 이것은 렌더링·접근성·실제 실행 성공을 대신 검증하지 않는다. resource의 저장 경합·실패·권한 테스트 통과 보고는 담당자 보고이며 product가 동일 테스트를 재실행한 결과는 아니다. MCP 테스트는 수행하지 않았다.

### 실제 화면 관찰

위 캡처만으로는 키보드 포커스 대비, 200% 확대, 정확한 클립보드 URL, 상태 변경·로그아웃·재연결의 성공을 판정할 수 없다.

후속 root의 실제 브라우저 보고: Mock 주소 복사가 전체 URL과 정확히 일치함을 확인했고, 환경 텍스트의 중복 두 행에서 적용 버튼 비활성화, 미적용 상태에서 탭 이동 확인을 취소하면 원래 화면으로 돌아가는 동작을 확인했다. product가 이 동작을 직접 조작해 재현한 것은 아니다. 변수363개 중 특정 키 검색·수정 후 서버 저장 확인은 이 보고 시점에 진행 예정이므로 성공으로 기록하지 않는다.

### 실제 REST 데이터 검증

preview의 연결 상태가 격리 Docker `http://127.0.0.1:18080`을 가리키는지 확인한 뒤 기존 테스트 API 경로로 공간을 추가했다. 기존52개 공간의 ID가 모두 유지되고, 새468개를 더해 총520개인 것을 재조회했다. 기존 공간 이름은 변경하지 않았다.

API는 동일한 `결제팀` 생성 두 번째 요청을400으로 거부했다. backend 제약을 우회하지 않았으며 유사 이름 세 개로 조정했다. Windows 응답의 문자셋 해석 문제는 원문 응답을 UTF-8로 읽어 실제 한글 이름을 다시 확인하고 fixture 메타데이터를 바로잡았다.

fixture는 `.run/agent-lab/preview/ui-scale-extended.json`에 원래 ID, 새 ID·이름, 총수, 동명 제약을 기록했다. 자격 증명은 출력하지 않았다. 이 결과는 520개 목록 검색·페이지 이동의 브라우저 성공을 의미하지 않는다.

## 남은 사용자 여정 검증

1. 처음 설치한 PC에서 서버 연결 없이 개인 Mock과 HTTP 흐름을 만들고 실제 결과를 확인한다.
2. 회사 로그인·승인 대기·승인 완료·팀 미참여 상태를 혼동 없이 구분한다. 로그인 실패가 개인 작업을 숨기지 않는다.
3. 520개 공간에서 유사 이름·ID 검색, 즐겨찾기·최근·페이지 이동, 공간 전환 뒤 원래 기능으로 돌아가는 동작을 확인한다.
4. 팀 A 저장 흐름의 PC 노드와 팀 B 서버 노드에서 실제 환경·Mock·시크릿 범위가 계획과 실행에 일치하는지 확인한다. 시크릿 값은 로그에 노출되지 않는다.
5. 환경 로드·저장 실패, 권한 철회, 자원 삭제에서 누락 값 실행이나 공용 공간으로의 조용한 대체가 없는지 확인한다.
6. Mock 주소 복사가 전체 URL과 일치하는 것은 root의 실제 브라우저 확인 보고로 완료. product의 확인 범위는 실제 캡처의 주소·복사 동선이다.
7. 최신 압축 자원 화면의 작업 영역 기준은 product의 실제 이미지 재확인으로 완료. 1280×720에서 변수8줄·환경9줄이 읽히고 활성·저장 상태를 유지한다. 특정 키 수정의 서버 영속성은 별도 검증이다.
8. Tab·Escape·포커스 복귀, 읽기 전용 행동, 초안 이탈, 확대·긴 이름·오프라인·재연결을 실제 브라우저로 확인한다.

완료되지 않은 항목을 승인이나 사용성 검증 성공으로 표현하지 않는다. 최종 빌드·배포 가능 여부와 backend 통합 테스트는 root의 릴리스 기록에 근거한다.
