# 코틀린 이관 검토 (백엔드)

> ✅ **이관 완료 (2026-07-05)** — 이 검토서의 방향대로 백엔드 전체가 Kotlin 으로 이관됐다(Java 0, `src/main/kotlin`·`src/test/kotlin`). 아래는 착수 전 검토 기록(역사).

백엔드(Java 21 / Spring Boot 3.3.5)를 Kotlin으로 이관하는 방안 검토. **"짧게 줄이기" 리팩토링과 코틀린 이관은 겹친다** — 코틀린으로 옮기면 소스가 자연히 간결해지므로, Java 리팩토링을 따로 하기보다 이관에 통합하는 것이 효율적이다.

> 이 문서는 방향 제안이며, 실제 착수는 승인 후. `build.gradle.kts` 변경(Kotlin 플러그인)이 필요해 되돌리기 부담이 있어 코드 변경 전 검토를 남긴다.

---

## 왜 코틀린인가

- **간결성**: `record`·getter/setter·생성자 보일러플레이트가 `data class` 한 줄로. 아래 예시 참조.
- **널 안전**: `Optional<T>` → `T?` + `?.`/`?:`. NPE를 타입으로 방어.
- **표현식 함수·when**: switch/if 사슬 → `when` 식, 짧은 메서드는 `= expression`.
- **Spring 1급 지원**: Spring Boot는 Kotlin을 공식 지원(코드 예제도 Kotlin 병기). JPA/Jackson 플러그인 성숙.
- **점진 이관 가능**: Java와 **같은 모듈에서 혼용** — 파일 단위로 `.java`→`.kt` 교체, 한 번에 안 바꿔도 됨.

---

## 간결화 예시 (before → after)

**DTO (record → data class)**
```java
// Java — FlowSummary.java (전체 파일)
public record FlowSummary(UUID id, String name, String description,
        int currentVersion, UUID folderId, Instant updatedAt) {
    public static FlowSummary from(Flow f) {
        return new FlowSummary(f.getId(), f.getName(), f.getDescription(),
                f.getCurrentVersion(), f.getFolderId(), f.getUpdatedAt());
    }
}
```
```kotlin
// Kotlin
data class FlowSummary(val id: UUID, val name: String, val description: String?,
    val currentVersion: Int, val folderId: UUID?, val updatedAt: Instant) {
    companion object {
        fun from(f: Flow) = FlowSummary(f.id, f.name, f.description,
            f.currentVersion, f.folderId, f.updatedAt)
    }
}
```

**Optional → nullable**
```java
// Java
Flow flow = flowRepo.findByIdAndTenantId(id, tenant())
        .orElseThrow(() -> NotFoundException.of("Flow", id));
```
```kotlin
// Kotlin
val flow = flowRepo.findByIdAndTenantId(id, tenant())
    ?: throw NotFoundException.of("Flow", id)
```

**노드 타입 switch → when** (FlowExecutor.processNode 같은 곳)
```kotlin
val result = when (node.effectiveType()) {
    START, END -> NodeResult.ok(...)
    SET        -> setNode(node, ctx)
    IF         -> ifNode(node, ctx)
    HTTP       -> http.execute(node, ctx)
    ...
}
```

체감상 DTO·값 record·enum·짧은 서비스는 **20~40% 라인 감소**, 긴 실행기(FlowExecutor 654줄·HttpNodeExecutor 510줄)는 널 처리·when·표현식으로 **10~25%** 정도 기대.

## 이관 규모 (백엔드 파일 카테고리)

| 카테고리 | 예 | 난이도 | 비고 |
|---|---|---|---|
| enum | ExecutionStatus·TriggerType·NodeType | ★ 쉬움 | 거의 1:1 |
| DTO record | FlowSummary·ExecutionSummary·Pending* | ★ 쉬움 | data class, jackson-module-kotlin 필요 |
| 값 record | Binding·NodeField·GraphNode | ★★ | GraphNode는 필드 많음(평탄 집약) |
| JPA 엔티티 | Flow·Execution·FlowVersion | ★★★ | no-arg/all-open 플러그인 필수, 지연로딩 open |
| 서비스·컨트롤러 | FlowService·ExecutionService | ★★ | 트랜잭션·주입 그대로 |
| 실행 엔진 | FlowExecutor·HttpNodeExecutor·TokenResolver | ★★★ | 로직 밀도 높음 — 이관 시 회귀 테스트 필수 |
| 설정·인프라 | SecurityConfig·common | ★★ | Bean 정의 all-open |

총 대략 **50~60개 파일**. 테스트 4종(ExpressionEvaluator/SsrfGuard/TokenResolver/MockRuntime)은 이관 대상 로직의 안전망.

## 필요한 빌드 설정 (`build.gradle.kts`)

```kotlin
plugins {
    kotlin("jvm") version "2.0.x"
    kotlin("plugin.spring") version "2.0.x"   // all-open: @Component/@Transactional 등 open
    kotlin("plugin.jpa") version "2.0.x"      // no-arg: JPA 엔티티 기본생성자
    // 기존 java/spring-boot 플러그인 유지
}
dependencies {
    implementation("com.fasterxml.jackson.module:jackson-module-kotlin")
    implementation("org.jetbrains.kotlin:kotlin-reflect")
}
// src/main/kotlin 소스셋 추가(또는 java 디렉토리에 .kt 혼용)
```
- 기존 한글 경로 cp949 테스트 이슈(ASCII 정션 `flwork`)는 코틀린에서도 동일 — 회피책 유지.

## 리스크

1. **JPA 엔티티** — `data class` 지양(equals/hashCode·지연로딩 함정). 일반 `class` + `plugin.jpa`(no-arg)·`plugin.spring`(all-open) 필요. 엔티티는 **후순위**로.
2. **Jackson** — `data class` 역직렬화에 `jackson-module-kotlin` 필수. GraphNode 라운드트립 회귀 확인 필요.
3. **빌드 시간·툴체인** — Kotlin 컴파일 추가. 한글 경로 이슈는 그대로.
4. **혼용 기간 일관성** — 이관 중 Java/Kotlin 공존. 컨벤션 문서화 필요.
5. **실행 엔진 회귀** — FlowExecutor/HttpNodeExecutor는 로직 밀도가 높아 이관 시 e2e(demos 47건)·단위 테스트로 반드시 검증.

---

## 권장 순서 (점진 이관 — 낮은 리스크부터)

1. **PoC**: `build.gradle.kts`에 Kotlin 플러그인 + enum 2~3개 + DTO record 1~2개를 `.kt`로. **Java/Kotlin 혼용 빌드·단위 테스트 통과 확인**. ← 여기서 감을 보고 확대 결정.
2. DTO·값 record 전체 → data class (jackson-module-kotlin).
3. 서비스·컨트롤러 (얇은 계층).
4. 실행 엔진 (FlowExecutor·노드 실행기) — 회귀 테스트 집중.
5. JPA 엔티티 (마지막, no-arg/all-open 검증).

각 단계마다 `compileJava`+`compileKotlin`·단위 4종·demos e2e로 검증하며 진행.

---

## 결론

- 코틀린 이관은 **"긴 소스 짧게" 요구를 근본적으로 해결**한다(보일러플레이트 제거).
- 큰 변경이므로 **PoC(1단계)로 시작**해 혼용 빌드가 매끄러운지 확인한 뒤 확대하는 것을 권장.
- Java 리팩토링을 별도로 하면 이관 시 재작성되므로, **코틀린 이관을 택한다면 Java 리팩토링은 보류**하는 것이 효율적.
